- PDFテンプレート・IPAexゴシックは `assets/`、画面・CSSは `app/templates/`・`app/static/`。現在は各モジュールの `__file__` から参照している。

- PDFはメモリ上で合成してinline応答。1枚目と2枚目14項目は実装済み。利用者による実ブラウザ確認も完了。
- 直前のpytestは183件成功。この計画作成ではテストを再実行しない。
- 古いサーバーと新しいHTMLが混在し500になった事例がある。更新は必ずアプリ終了後に配布フォルダ全体を交換する。
- DBモデル、Assessment履歴、client_snapshot、PDF座標・mapping・描画方式を変更しない。

## 2. 推奨する最小配布構成

PyInstallerのWindows用 `onedir` + `windowed`（console=False）、内部ディレクトリ名 `_internal` を推奨。
ビルド対象はまずWindows x64。対応OSは事業所PC確認後に確定し、Windows 11 x64を初期検証対象とする。

```text
独自アセスメント/
  アセスメント.exe
  _internal/
    Pythonランタイム・DLL・依存ライブラリ
    app/templates/
    app/static/
    assets/pdf_templates/assessment_form.pdf
    assets/pdf_templates/assessment_checksheet.pdf
    assets/fonts/ipaexg.ttf
    assets/fonts/IPA_Font_License_Agreement_v1.0.txt
    assets/fonts/Readme_ipaexg00401.txt
    licenses/                 # その他同梱物の必要なライセンス
```

デスクトップへファイルをばらまかず、このフォルダ全体を渡す。利用者はexeのみ操作する。
初回のZIP展開・配置・既存DB引継ぎ・更新は導入担当者が行う。利用者へコマンド操作を要求しない。
実DB、検証DB、`.git`、`.venv*`、`.tools`、テスト、ログ、確認用PDFは配布物へ含めない。

| 方式 | 判断 |
|---|---|
| onedir | 採用案。内部ファイルをまとめられ、毎回の一時展開が不要。欠落資産の調査も容易 |
| onefile | 初版では不採用。一時展開と起動時間・終了時の処理が増え、1フォルダ要件への利点が小さい |
| インストーラー/MSIX | 初版では後回し。まずフォルダ配布で検証する |

公式資料: [PyInstaller使用方法](https://www.pyinstaller.org/en/stable/usage.html)、[実行時パス](https://www.pyinstaller.org/en/stable/runtime-information.html)。

## 4. 起動から終了まで

### 起動

1. exeをダブルクリック。シェルや別のpython.exeを起動せず、同一プロセス内で処理する。
2. データ領域とローテーション付きファイルログを準備。書込不可なら日本語ダイアログで停止する。
3. アプリIDとWindowsユーザーに対応する名前付きmutexを取得。同じデータを使う配布フォルダのコピーも同一アプリとして扱う。
4. 起動済みなら、保存されたポートだけを信用せずアプリ識別子・起動トークンで既存インスタンスを確認し、その画面を開いて二重起動側は終了する。
5. 初回設定を完了し、DBを開く。DB・資産の検証に失敗したらブラウザを開かず、日本語メッセージとログの保存場所を示す。
6. `127.0.0.1:8000` のソケット確保を試す。別プロセスが使っている場合は終了させず、OS割当ての空きポート（port=0）を確保する。
7. 確保したソケットをUvicornへ渡す。空き確認後に閉じて再確保する方式は競合するため使わない。
8. `create_app(database_url=..., desktop_runtime=...)` で作ったアプリを `uvicorn.Config` / `Server` で起動する。workers=1、reload=False、loop=asyncio、HTTP実装を固定し、不要な動的依存を減らす。
9. DB初期化を含む起動完了と、このインスタンスへのHTTP疎通を制限時間内に確認する。その後、標準 `webbrowser` で既定ブラウザを開く。固定秒数待機だけで起動成功としない。
10. タイムアウト・ブラウザ起動失敗はファイルへ記録し、日本語ダイアログで再試行または終了を案内する。URL手入力を通常手順にしない。

参考: [Uvicornのプログラムからの起動](https://www.uvicorn.org/deployment/)。

### 終了

- 画面共通の「アプリを終了する」をクリックし、確認後にPOSTする。GETアクセスだけで停止しない。
- 他サイトからの停止要求を防ぐため、起動ごとのトークンとOrigin等を検証する。制御用トークンはアクセスログや通常URLへ出さない。
- 終了ページを返した後、Uvicornへ終了を要求する。処理中リクエストの完了、lifespan終了によるDB接続解放、ソケット・mutex・実行情報の解放、ログflushを行う。
- 通常終了で強制killを使わない。終了できない場合は利用者へ通知し、保存を中断する自動強制終了を避ける。
- ブラウザタブを閉じただけではサーバーを終了しない。複数タブや一時切断で停止しないための仕様。
- 誤ってブラウザを閉じた場合はexeを再度ダブルクリックすれば既存画面を再表示し、終了操作ができる。
- 起動途中の二重クリック、終了中の再起動、異常終了後の古い実行情報を処理する。PIDだけで他プロセスを終了させない。

## 5. データ保存方法

推奨案: `%LOCALAPPDATA%\AssessmentApp\`。製品バージョンをパスに含めず、exeの場所にも依存させない。

```text
%LOCALAPPDATA%/AssessmentApp/
  data/assessment.sqlite3
  backups/                     # 引継ぎ・更新前のバックアップ
  logs/app.log                 # 例: 2 MB × 5世代
  runtime/instance.json         # ポート・起動識別子等。DBではない
  setup.json                   # 初回設定済みの記録
```

- この案は「同じWindowsユーザーで使うローカルアプリ」を前提とする。別Windowsユーザー・別PCとのDB共有は実現しない。事業所全体の共有要件があれば保存先だけで解決せず別設計とする。
- 配布フォルダを削除・更新してもデータ領域は削除しない。配布フォルダやOneDrive同期フォルダへ実DBを置くことを標準運用にしない。
- 配布版でもDBテーブル・カラム・履歴の意味は同じ。今回スキーママイグレーションは追加しない。
- PDFは従来どおりメモリ応答。ブラウザから保存したPDFは利用者が選んだ保存先に置かれる。

### 初回・既存DB引継ぎ

- 初回だけ日本語ダイアログで「新しく利用する」「既存データを引き継ぐ」を選べるようにする。通常利用者への設定負担は導入担当者が先に済ませる。
- 新規利用を選んだ場合だけ、既存の `init_db` で空DBを作成する。
- 引継ぎは元アプリ停止後に行う。元DBを変更・移動せず、読み取り専用接続とSQLite backup APIで一時コピーを作る。単純コピーによるWAL取りこぼしを避ける。
- 整合性、想定テーブル・カラム、主要テーブルの件数を確認し、成功後だけ未使用の移行先へ確定する。既存の移行先DBは上書きしない。
- 破損・不適合DBを新規DBへ置き換えて起動する挙動は禁止。設定済みなのにDBがなくなった場合も、新規作成せず復旧案内で停止する。
- 開発版の既定保存先はそのまま。配布版への引継ぎ後にどちらを本運用とするかを明記し、二つのDBへの分散入力を防ぐ。

### 更新・バックアップ

- アプリ終了 → DBバックアップ確認 → 新しい配布フォルダ全体へ交換 → exe起動 → 既存データ確認、を担当者の手順とする。稼働中の部分上書きはしない。
- 起動時に記録したアプリバージョンとの相違を検出したら、DBを変更する前にSQLite backup APIで世代バックアップを作る。失敗時はそのまま起動を続けない。
- 初版ではスキーマ変更なし。将来スキーマ変更する版は移行・ロールバック方針を別途策定する。`create_all` はスキーマ移行機構として扱わない。
- 同じディスクのバックアップだけではPC故障に対応できない。事業所が承認する外部バックアップ先・担当者・頻度を本番導入前に決める。自動クラウド送信は追加しない。

## 6. リソースとログ

- `app/paths.py` で開発時はリポジトリroot、frozen時はPyInstaller bundle rootを返す。通常の起動ディレクトリやユーザー名の固定値に依存しない。
- specのdatasは `assets/pdf_templates`、`assets/fonts`、`app/templates`、`app/static` の構造を維持して明示指定する。
- 読込資産は一切書き換えない。起動時に必要なPDF2点・フォント・HTML/CSSが存在することを確認する。
- 日付、バージョン、起動段階、例外tracebackをローテーション付きファイルへ出す。フォーム本文、氏名、アセスメント内容、PDF内容、制御トークンは記録しない。通常アクセスログは無効または個人識別情報を除く。
- console=Falseでは標準出力・標準エラーが利用できない場合があるため、Uvicornを含めStreamHandler依存を避け、ファイルhandlerを先に設定する。
- ログ初期化自体が失敗した場合もコンソールに依存せずダイアログで通知する。

## 7. exe化手順（実装時に開発者だけが行う）

1. 対象Windows x64で専用のクリーンなビルド用venvを作る。既存開発venvを配布しない。
2. Python、実行依存、PyInstaller、hooksの動作する組合せを固定する。最新版という理由だけで採用しない。
3. 起動・終了・パス分離を実装し、既存pytestと追加テストを全件実行する。
4. specにconsole=False、onedir、contents_directory='_internal'、upx=Falseを設定する。必要なhidden importsは凍結実行の結果から最小限追加する。
5. 開発者が `python -m PyInstaller --clean packaging/assessment.spec` を実行する。出力先は `dist/独自アセスメント/` を予定。
6. 同梱物と原本ハッシュを照合。実DBや個人情報、検証成果物が入っていないことを自動検査する。
7. PythonのないクリーンWindowsで検証する。必要なら修正して同じ手順で再ビルドする。
8. 配布物のハッシュ・バージョンを記録。導入対象PCのDefender等で検査し、署名方針に従って署名・検証する。
9. フォルダ全体をZIP等で渡し、担当者が展開してショートカットを任意作成する。利用者はexeをダブルクリックするだけにする。

## 8. テスト計画と受入条件

### 自動テスト

- 既存全件を維持。1枚目・2枚目14項目、履歴分離、overflow、原本・DB非更新を再確認。
- 開発/frozenで資産パスとデータパスが分離すること。日本語・空白パス、別作業ディレクトリ、読取専用配布フォルダを検証。
- 新規DB作成、引継ぎ、既存移行先、破損、移行失敗、DB消失、権限不足でデータが失われないこと。
- 起動完了前にブラウザを開かない、8000競合時の代替ポート、多重起動、異常終了からの再起動、終了時リソース解放を検証。
- 終了ルートがGETや無効トークンでは動作せず、通常開発起動には存在しないこと。
- noconsole相当の標準出力なし状態でもログ・例外処理が動くこと。

### 配布exeの実機試験（pytestだけでは代替しない）

- Python・Gitなし、標準ユーザー、管理者権限なしでダブルクリック起動。
- 起動中・動作中・終了時にコンソールが一瞬も出ない。
- 既定ブラウザが自動起動し、利用者登録・Assessment保存・再編集・再アセスメント・14項目の保存が可能。
- 1枚目・2枚目PDFがinline表示される。日本語・縮小・枠位置を画像と画面で確認し、A4・100%で紙への試し刷り。
- 8000が別アプリ使用中でも起動し、そのアプリを停止しない。ネットワーク切断中でも利用できる。
- 連続ダブルクリック、ブラウザを閉じて再度exe起動、終了後の再起動、PC再起動で利用可能。
- 終了後にサーバープロセス・待受ポートが残らない。ブラウザタブを閉じるだけの場合は再表示可能。
- 配布フォルダ全交換後も、同じ利用者・Assessment履歴・snapshot・Checkデータを確認できる。
- DB・資産欠落、ディスク容量不足、ブラウザ関連付け失敗を利用者向けに通知できる。
- 実際の事業所PCのWindowsセキュリティ設定で起動できる。ネットワーク公開用の受信許可やDefender無効化を利用者へ要求しない。

## 9. 主なリスク

| リスク | 対応 |
|---|---|
| 凍結後だけ依存モジュールが不足 | Uvicornの構成固定、spec調整、クリーンPCでのexe試験 |
| 保存先変更で空DBに見える | 初回の明示選択、安全な引継ぎ、設定済みDB消失時の停止 |
| 更新で旧プロセスが残る | 明示終了とmutex。起動中フォルダを上書きしない |
| ブラウザを閉じても常駐する | 「アプリを終了する」の案内とexe再クリックによる復帰 |
| 別Windowsアカウントでデータが見えない | LocalAppDataのユーザー別仕様を事前確認。共有運用は別設計 |
| Defender誤検知・SmartScreen警告 | UPX無効、安定した製品情報、清潔なビルド、署名検討、対象PCで確認、必要時は正式な誤検知申請 |
| PC故障・データ紛失 | 更新前バックアップと事業所の外部バックアップ運用 |

署名やonedir採用で警告・誤検知が必ず消えるとは保証しない。SmartScreenの評判判定とマルウェア検知は区別する。
コード署名の費用・発行者・鍵管理は実装前に確定せず、本番配布の判断事項とする。
参考: [MicrosoftのSmartScreen開発者向け説明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)。

## 10. 実装範囲と保留

次回の最小配布版に含める案:

- onedir/windowed、資産同梱、リソース参照集約。
- 自動起動・起動確認・ブラウザ表示、ポート競合対応、単一起動、明示終了、ファイルログ。
- 配布版の永続データ領域、初回新規作成・既存DB引継ぎ、更新時バックアップ。
- 開発起動互換、全件テスト、クリーンWindows試験、簡潔な導入・更新案内。

後回し:

- onefile、インストーラー、Windowsサービス、タスクトレイ、自動起動登録、自動アップデート。
- 複数PC/複数Windowsユーザーでの共有DB、クラウド同期、認証基盤、DBスキーマ変更。
- PDF2ページ結合、座標・mapping変更、アプリによる生成PDFの自動保存。

実装前に確認する重要事項:

1. 対象PCのWindowsバージョン・CPUアーキテクチャ。
2. 同一Windowsユーザーでの運用でよいか。複数アカウント間・複数PC間のデータ共有が必要か。
3. LocalAppDataへの保存、終了ボタン方式、初回導入・引継ぎ・更新を担当者が行う方針の可否。
4. 引継ぐ既存DBの所在、運用を切り替える時点、バックアップ責任者と外部保存先。

この計画で保存先・署名・共有運用を確定済みとして扱わない。計画の確認後に実装を開始する。
